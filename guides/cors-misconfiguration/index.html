CORS misconfiguration: how one header lets any site read your API

Updated Oct 22, 20268 min read

A CORS misconfiguration (CORS decides which sites may read your API's responses) happens when your API lets any website read them, usually by copying the request's Origin header back with credentials on. A page on evil.example can then read a logged-in user's data. Fix it with an exact list of allowed origins. CORS is not security: tools like curl ignore it, so check logins on the server.

QUICK CHECKLIST

  • Never combine origin: true with credentials: true
  • Allow exact origins from a list, not regexes
  • Never allow the null origin
  • Send Vary: Origin when the header changes per request
  • Use * only for public data with no cookies
  • Check auth on the server, not with CORS

What a CORS misconfiguration is and why it matters

CORS is a browser rule. When a script on one site asks another site for data, the browser checks the response headers before it lets the script read the answer. Access-Control-Allow-Origin names the sites that may read it, and Access-Control-Allow-Credentials: true lets the script read responses to requests that were sent with cookies.

A CORS misconfiguration is a policy that names too many sites. The usual version is a server that copies the request's Origin header (the browser's note of which site the request came from) into Access-Control-Allow-Origin while credentials are on. Any website your logged-in user visits can then call your API as that user and read the result whenever the browser sends the session cookie cross-site, which is the case for SameSite=None cookies, the usual setting when the frontend and API live on different domains.

How attackers abuse a bad CORS policy

A logged-in user opens a page the attacker controls. A script on that page calls your API with credentials: "include", your server answers with a permissive header, and the script reads the response. PortSwigger's examples show attackers pulling API keys and CSRF tokens out of responses this way.

These are the usual ways the policy goes wrong:

  • A reflected origin. In Express cors, origin: true copies the request's Origin into Access-Control-Allow-Origin. Add credentials: true and every website can read logged-in responses. OWASP calls reflecting the origin without checks very insecure. The only exception it gives is a public API meant for everyone, and that never applies when credentials are allowed.
  • Wildcard plus credentials. Browsers refuse Access-Control-Allow-Origin: * when credentials are involved, so the call fails in development. Reflecting the origin makes the error go away and opens the hole.
  • The null origin. Browsers send Origin: null from sandboxed iframes, file: pages, some redirects and serialized data. Developers allow it for local testing, but an attacker can send it on demand from a sandboxed iframe, so it works like a wildcard.
  • A regex with a loose end. /myapp\.com$/ also matches https://hackersmyapp.com. A check without the $ matches https://myapp.com.evil.example. Both patterns appear in the PortSwigger and OWASP write-ups.

A correct allowlist still trusts every site on it. If an allowed subdomain has XSS (cross-site scripting, where an attacker gets their own script to run on your page), the attacker runs script there and reads your API from it. An allowed http:// origin is weaker for the same reason: someone on the network can inject a page that sends that origin.

WATCH OUT

Internal tools count too. A wildcard on a site that only lives on a private network still lets an outside page reach it through a visitor's browser.

Express and Next.js: before and after

The Express cors() call with no options sends Access-Control-Allow-Origin: *. That's fine for public data. The trouble starts when a CORS error shows up in the console and someone adds credentials: true and origin: true to silence it.

Next.js route handlers have no CORS middleware, so you set the headers yourself. The same rule applies: echo an origin only when it's on your list.

TIP

If your frontend and API are served from the same origin, for example one Next.js app calling its own /api routes, you need no CORS headers at all. Delete the config.

How to fix a CORS misconfiguration, step by step

  1. Check whether you need CORS

    Same-origin calls never need it. Only add CORS when a different site or domain calls your API from a browser.

  2. Write the origins down

    List each origin exactly: scheme, host and port, such as https://myapp.com. No wildcards, no regexes, no null. Keep the list in an env variable like ALLOWED_ORIGINS. Add http://localhost:3000 only in your local .env, never in production.

  3. Compare, then echo

    Send Access-Control-Allow-Origin only when the request's Origin is an exact match for an entry. For any other origin, send no CORS headers at all.

  4. Add Vary: Origin

    When the header value changes per request, add Vary: Origin. Otherwise a cache can hand one site's permission to another. The Express docs show Vary: Origin on their single-origin and dynamic examples.

  5. Keep * for public data only

    A public endpoint with no cookies, like a product list, can use Access-Control-Allow-Origin: *. Don't put it next to credentials or private data.

  6. Check auth on the server

    Every handler that returns private data should check the session and ownership itself. See IDOR in API routes for the usual gaps.

CORS is not security: curl ignores it

CORS only decides whether a browser lets a page read a response. Your server still receives and handles every request. The Express cors docs say it plainly: curl, Postman and other servers ignore CORS entirely.

So a tight allowlist doesn't protect an endpoint that has no auth. Anyone can run curl https://yourapp.com/api/users and read the answer. Anyone can also set an Origin header by hand, and OWASP warns against relying on it for access control.

Simple requests, such as form-style POSTs, go out without a preflight, so a page on another site can still make your server act. PortSwigger states that CORS is no protection against CSRF, where another site makes a user's browser send a state-changing request with their cookies.

Check sessions in each handler, and see Next.js middleware authentication for why a middleware check alone can fall short. If you keep tokens in the browser, read JWT in localStorage vs cookies too.

NOTE

Cookie settings such as SameSite can change what a browser sends cross-site. Don't count on them to cover for a bad CORS policy.

Test it yourself

Replace the placeholders with your domain and a session cookie from your own logged-in browser (or an Authorization header if you use one).

WATCH OUT

Only test apps you own. Don't point these requests at someone else's site.

The loop sends five Origin values: your real one, a stranger, null, and two lookalikes. curl doesn't enforce CORS, so it just shows which headers your server sends. The browser applies the rule.

for o in https://myapp.com https://evil.example null https://myapp.com.evil.example https://evilmyapp.com; do
  echo "== Origin: $o"
  curl -s -i https://YOUR-APP.com/api/me \
    -H "Origin: $o" \
    -H "Cookie: YOUR_SESSION_COOKIE" | grep -iE "^(access-control|vary)"
done

A bad result is any access-control-allow-origin line that repeats the stranger, null or lookalike origin, especially next to access-control-allow-credentials: true. A good result shows no access-control-allow-origin line for those four. Your real origin should be echoed back, with vary: Origin present.

Then check in a browser. Open DevTools on a tab for an unrelated site while you're logged in to your app, and run:

fetch("https://YOUR-APP.com/api/me", { credentials: "include" })
  .then((r) => r.json())
  .then(console.log)

If your user data prints, the policy is open. If no data prints, look at the Network tab before you relax. A CORS error means the browser blocked the read. A 401 or empty response with an access-control-allow-origin header that matches the unrelated site means the policy is still open, and your cookies just weren't sent (SameSite=Lax/Strict or third-party cookie blocking). Treat the curl results above as the authoritative check. Some sites have a Content Security Policy that blocks this fetch, so use a local test page if that happens.

TIP

If you run GitHub code scanning for JavaScript, CodeQL has a query named js/cors-misconfiguration-for-credentials that targets the dynamic-origin-plus-credentials pattern.

FAQ

What is a CORS misconfiguration?

It's a CORS policy that lets websites read your API's responses when they should not be allowed to. Common causes are reflecting the Origin header, allowing null, and loose regex allowlists, especially with Access-Control-Allow-Credentials: true.

Is Access-Control-Allow-Origin: * a vulnerability?

Not by itself. It's fine for public data that needs no cookies, and browsers refuse it when credentials are involved. It becomes a problem when the response is private, or when the app sits on a private network and relies on that network for protection, because a visitor's browser can carry an outside page's request in.

Does CORS protect my API from curl or Postman?

No. CORS is enforced by browsers, and curl, Postman and other servers ignore it. Your server still receives every request, so protect private endpoints with authentication and authorization.

How do I allow multiple origins in Express cors?

Pass an array of exact origin strings, such as ["https://myapp.com", "https://www.myapp.com"], or a function that checks the origin against your list. Avoid origin: true, which reflects any origin, and avoid regexes, which are easy to get wrong. Then run the curl loop from the test section to confirm the headers.

Why do I get a CORS error even though my server responded?

The browser blocked your script from reading the response because the CORS headers didn't allow your origin. JavaScript only sees that an error happened, so open the browser console for details. Fix the headers on the server, and handle the OPTIONS preflight if you send JSON, an Authorization header, other custom headers, or methods other than GET, HEAD or POST.
