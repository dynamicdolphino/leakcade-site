Vibe coding security checklist: 10 checks before you ship

Updated Oct 22, 20262 min read

This vibe coding security checklist has ten checks to run before you share your AI-built app with strangers. Each one comes with a way to test it in a few minutes and a guide if it fails. You don't need a security background, just a logged-out browser window, a second test account, and your repo and Supabase dashboard.

The 10-point vibe coding security checklist

#CheckHow to test it
1No secrets in code or git history (guide)Run gitleaks on the repo. Search the built JS for sk-.
2Every API route and server action checks who's callingCall it with curl and no cookie. Expect 401.
3Users can only access their own data (including deletes)With account B, change an id to account A's record.
4Database queries are parameterizedSearch for SQL built with template strings.
5CORS limited to your domainSearch for origin: "*" or Access-Control-Allow-Origin: *.
6Rate limits on login and AI endpointsSend 10 wrong passwords in a row. Expect a 429.
7Prices and roles checked on the server (not from user_metadata), payment webhooks verifiedSend a fake webhook without a signature. Nothing should change.
8Dependencies without known vulnerabilities, and no made-up packagesRun npm audit. Look up unfamiliar names on npm.
9Errors don't leak stack tracesBreak a request on purpose and read the response.
10Database rules (Supabase RLS) switched onQuery a table with the anon key while logged out.

Test it the way an attacker would

Most holes in AI-built apps show up in the first two passes. A logged-out request that returns data, or an edit that works on someone else's record, is a finding even if the UI never offers that button.

TIP

Run the checklist again after every change that touches auth, the database schema or payments. AI edits in one file often loosen a rule somewhere else.

FAQ

What is vibe coding security?

Checking an app you built by prompting an AI tool for the security holes those tools tend to leave: missing auth checks, open database rules, leaked keys and trust in the browser.

Which check matters most?

Checks 2, 3 and 10 cover who can read and change data, so start there if you only have ten minutes.

How often should I run this checklist?

Before launch, and again after any change to auth, database rules, payments or dependencies.

Can an AI tool run this checklist for me?

It can do a first pass with the prompt above. It can't log in as a second user and try the requests, so do passes 1 and 2 yourself.
