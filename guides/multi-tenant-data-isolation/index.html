Multi-tenant data isolation: stop one org reading another's data

Updated Oct 24, 20267 min read

Multi-tenant data isolation means a user in Org A can never read or change Org B's rows, even if they edit the request. It breaks when queries filter only by id or trust an org_id from the browser. Fix it with a server membership check plus Postgres row level security (RLS), a rule the database adds to every query. Then prove it with two orgs.

What multi-tenant data isolation means

Multi-tenant data isolation is the rule that every row belongs to one organization, and a user only reaches rows in organizations they belong to. Your SaaS keeps many customers in one database, so this rule is all that separates them. The column might be org_id or tenant_id. The job is the same.

OWASP's multi-tenant cheat sheet treats cross-tenant data leakage as a core risk, and OWASP ranks broken access control first in the Top 10:2025. A cross-tenant data leak is that bug with another customer's data exposed.

It takes three things: an org_id on every tenant table, a server-side membership check on every request, and RLS as the backstop when app code forgets.

How a cross-tenant data leak happens

The attacker is usually a paying customer with a valid login. They copy a request in dev tools and change one value. Common openings:

  • Lookups by id alone. findUnique({ where: { id } }) returns the row whatever org it belongs to. This is IDOR (reading someone else's record by changing an id) in API routes.
  • Org id taken from the client. A header, body field or cookie names the org and the server runs with it. Check it against the user's memberships on every request, so a removed member loses access immediately.
  • Invites. Accepting an invite writes to memberships. If the browser can insert there, or send role: "owner", anyone can join any org with any role.
  • Global roles. An is_admin flag makes an admin of Org A an admin everywhere. Keep the role in the membership row, not in [user_metadata](/guides/supabase-user-metadata/), which users can edit.
  • RLS that says yes to everyone. using (true) passes the "RLS is on" check and separates nothing. See common Supabase RLS mistakes.
WATCH OUT

A .eq('org_id', orgId) in browser code is optional. The Supabase anon key is public, so anyone can send the query without it. Only RLS and server checks are enforced.

Supabase RLS with an is_member() helper

Supabase RLS still holds when a route handler forgets its filter. The Supabase docs describe a policy as a WHERE clause added to every query. For orgs it asks one question, so put that question in one helper.

create schema if not exists private;
grant usage on schema private to authenticated;

create function private.is_member(_org_id uuid, _roles text[] default null)
returns boolean
language sql
security definer
stable
set search_path = ''
as $$
  select exists (
    select 1 from public.memberships m
    where m.org_id = _org_id
      and m.user_id = (select auth.uid())
      and (_roles is null or m.role = any (_roles))
  );
$$;
WATCH OUT

Put the helper in a schema your API does not expose, like private. A security definer function in public can be called through the API by anyone who can reach it.

The function is security definer, so it reads memberships with its owner's rights. Without that, a policy on memberships that queries memberships would trigger itself over and over. set search_path = '' stops another schema from shadowing table names, so the body uses public.memberships.

The first policy set below is what a quick "turn RLS on" fix leaves behind. The second ties every operation to membership.

Lock down memberships too. Clients may read their own rows and nothing else. Only your server creates memberships, using the service role key after it checks an invite. That key bypasses RLS, so it never goes in browser code. The insert policy guide shows how to stop users adding themselves to any org.

Prisma: a client scoped to one org

Prisma queries from a route handler usually skip your Supabase policies. Superusers and roles with BYPASSRLS bypass row security, and so do table owners unless the table uses FORCE ROW LEVEL SECURITY. The default postgres connection on Supabase falls in this group.

Prisma query extensions let you change the arguments of the operations you hook. Build one scoped client per request, after the membership check.

import { prisma } from "@/lib/prisma"

// Membership has @@id([orgId, userId])
export function getMembership(orgId: string, userId: string) {
  return prisma.membership.findUnique({
    where: { orgId_userId: { orgId, userId } },
  })
}

export function dbForOrg(orgId: string) {
  return prisma.$extends({
    query: {
      project: {
        async findMany({ args, query }) {
          args.where = { ...args.where, orgId }
          return query(args)
        },
        async findFirst({ args, query }) {
          args.where = { ...args.where, orgId }
          return query(args)
        },
      },
    },
  })
}

This snippet hooks only two operations. Hook findFirstOrThrow, count, aggregate, groupBy, updateMany and deleteMany the same way, and set orgId in the create, createMany and upsert hooks. Make findUnique, findUniqueOrThrow, update and delete throw on the scoped client, so an unscoped call fails loudly. For single-row changes, use updateMany or deleteMany so the org filter rides along.

Relations loaded with include are not filtered, and raw queries need their own handling. That is why the database layer matters too.

The org still arrives from the client, here in ?org=. That's fine, because the server checks it against the verified user first. With Supabase Auth, get the user with [getUser(), not getSession()](/guides/supabase-getsession-vs-getuser/).

How to fix multi-tenant data isolation, step by step

  1. Put org_id on every tenant table

    Include child tables. Make it not null, index it, and backfill old rows before you enable policies.

  2. Resolve the org on the server

    Treat the org id from the URL or a header as a hint. Load the membership for the verified user and return 403 if there isn't one, on every request.

  3. Scope every query

    Use a scoped client or one shared helper. Look rows up by id and org together, so a copied id from another org returns nothing.

  4. Turn on RLS with is_member()

    Enable RLS, revoke default grants and write one policy per operation that calls the helper. A table in an exposed schema (by default public) without RLS is open to any role with a grant on it.

  5. Lock down invites and roles

    Only your server creates memberships. Invite tokens are single-use, expire and match the invited email. Roles come from the membership row, never the request body.

  6. Add the two-org test

    Keep the checks from the next section in your repo and rerun them whenever you add a table.

Test it yourself with two orgs

Only run these against your own project and test accounts.

Create user A in Org A and user B in Org B, each org with one project. Sign in as A and copy the access token from dev tools. Anyone with your public anon key can call the Supabase API, so start there:

curl "https://YOUR_PROJECT.supabase.co/rest/v1/projects?select=id,org_id,name" \
  -H "apikey: YOUR_ANON_KEY" \
  -H "Authorization: Bearer USER_A_ACCESS_TOKEN"

Good result: only Org A's project. Bad result: Org B's project shows up too. Add &id=eq.ORG_B_PROJECT_ID to ask for B's row directly. You should get [].

Next, send a PATCH to the same endpoint, with ?id=eq.ORG_A_PROJECT_ID and the body {"org_id": "ORG_B_ID"}. Good result: an error and an unchanged row. Bad result: a 204 and the project now belongs to Org B.

Then call your own Next.js route as A with B's project id, once with ?org=ORG_A_ID and once with ?org=ORG_B_ID. Good results: 404, then 403. Bad result: a 200 with Org B's JSON. Finally, remove A from Org A and repeat the first call. The rows should be gone immediately.

FAQ

How do I do multi-tenant isolation in Supabase with RLS?

Put an org_id on every tenant table and keep a memberships table. Write a security definer helper such as is_member(org_id) and call it from one policy per operation. Then test with two users in two orgs.

How do I add a tenant_id check in a Next.js API route?

Treat the org id from the request as a selector. Get the verified user, look up their membership in that org, and return 403 if it's missing. Then run every query with that org id.

Is filtering by org_id in my query enough?

Only if the org id comes from a server-side membership check. Anyone calling the API directly can skip a filter written in browser code. Add RLS as a backstop.

Does Prisma respect Supabase RLS?

Usually not. Prisma connects as the role in your connection string, and policies don't apply to superusers, roles with BYPASSRLS, or table owners without FORCE ROW LEVEL SECURITY. That includes the default postgres user. Prisma also doesn't send the user's JWT, so auth.uid() is null. Use app-layer checks and a scoped client.
