GitHub Actions secrets: how AI-built repos leak them and how to lock CI down

Updated Oct 22, 20268 min read

GitHub Actions secrets stay private only if your workflows never hand them to code or text you don't control. Four patterns break that: pull_request_target (a trigger that runs with your secrets) with a checkout of pull request (PR) code, untrusted text in shell scripts, a loose GITHUB_TOKEN, and unpinned third-party actions. Fix those and you close the most common ways an outsider's pull request or issue can reach your keys.

QUICK CHECKLIST

  • Keep keys in secrets, never in workflow files
  • Use pull_request, not pull_request_target, to build PRs
  • Pass issue and PR text through env vars, never inline
  • Set GITHUB_TOKEN to contents: read, raise it per job
  • Pin third-party actions to a full commit SHA
  • Put deploy keys in an environment with reviewers

What GitHub Actions secrets protect and what can reach them

GitHub Actions secrets are encrypted values you store in repository, environment or organization settings. Your workflow reads them with ${{ secrets.NAME }} and uses them to deploy, publish a package or call an API from CI.

If you build solo with an AI tool, you probably have one repo, one deploy key and a workflow file you never read. That's fine until someone else's text or code reaches that workflow, because then everything the job can read is in play.

Anyone with write access to your repository can read all of its secrets. A compromised action in your workflow would have access to all secrets configured on the repository, and it may be able to use the GITHUB_TOKEN (a temporary access token GitHub creates for each workflow run) to write to it.

How attackers reach your CI secrets

Every attack here gets the attacker's code or text into a job that holds your secrets. There are four routes.

  • A privileged trigger plus PR code. pull_request_target runs with write permission to your repo and access to its secrets. If the workflow also checks out the pull request's code and runs npm install, the attacker decides what runs. GitHub Security Lab calls these pwn requests (a pull request that takes over your workflow). The idea resembles an npm supply chain attack: untrusted code runs where your secrets are.
  • Script injection. If you write ${{ github.event.issue.title }} directly inside a run: step, the value is pasted into the shell script before it runs. Anyone who can open an issue can put shell syntax in the title.
  • A compromised third-party action. Jobs in a workflow can interact with each other, so one bad action can reach the secrets of every job. A tag like @v1 can be moved or deleted if someone gets into the action's repo.
  • Secrets typed into the workflow file. Anyone who can read the repo can read them, and a public repo means everyone. That's a plain leaked API key sitting in YAML.
NOTE

With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository. Plain pull_request also blocks write permissions for forks.

SecretsWrite access
pull_request from a forkNoNo
pull_request from the same repoYesYes
pull_request_targetYesYes
workflow_runYesYes

Based on GitHub Security Lab's pwn requests post. Actual token write access also depends on your repo/org default workflow permissions and any permissions: block.

WATCH OUT

Fixing a vulnerable workflow doesn't fix pull requests that are already open. They keep using the workflow version from when they were opened, so close or rebase any PR that could still receive untrusted commits.

How to lock down GitHub Actions secrets, step by step

Work through your workflow files in this order.

  1. Move keys into secrets

    Run gh secret set STRIPE_SECRET_KEY, paste the value when asked, and reference it as ${{ secrets.STRIPE_SECRET_KEY }} in an env: block. Create one secret per value, because redaction relies on exact matches and a JSON blob can slip past it. Treat any key that was ever typed into a workflow file as leaked and rotate it.

  2. Limit GITHUB_TOKEN permissions

    Add permissions: contents: read at the top of each workflow. Raise it for single jobs that need more, such as issues: write. Without a permissions: block the token gets your repo or organization default, so check that default in your Actions settings.

  3. Replace pull_request_target

    Use plain pull_request to build and test PRs. If you only need to label or comment, pull_request_target is fine as long as it never checks out or runs the PR's code.

  4. Put untrusted text in env vars

    For issue titles, PR titles, bodies and branch names, set env: TITLE: ${{ ... }} and use "$TITLE" in the script. Never put the expression inside the run: text.

  5. Pin actions to a commit SHA

    GitHub's strongest option is a workflow dependency lockfile, which also covers actions that your actions call. If you can't adopt one, write the full-length commit SHA (the 40-character ID of one exact version of the action's code) after the @, with the version in a comment, like uses: actions/checkout@FULL_40_CHAR_SHA # v4. A SHA pin does not cover what that action calls internally. Copy the SHA from the action's own repository, not from a fork.

  6. Gate deploy keys behind an environment

    Create an environment (a named deployment target with its own secrets and approval rules) such as production under Settings, then Environments. Store the key with gh secret set STRIPE_SECRET_KEY --env production, add environment: production to the deploy job and require reviewers. Check your plan first, because required reviewers for private repositories aren't available on GitHub Free.

Also list .github/workflows in a CODEOWNERS file (a file that names who must approve changes to given paths) so workflow changes need a reviewer. If your cloud provider supports OpenID Connect (short-lived logins issued per run), use it instead of long-lived cloud credentials.

Split privileged work from untrusted PR code

To comment on every PR, GitHub Security Lab describes a safe pattern. One workflow runs on pull_request with no secrets and a read-only token, and a second runs on workflow_run with the write access.

The first workflow builds the PR and saves a small result as an artifact (a file a job uploads so later workflows can download it). The second downloads it and posts the comment. Treat that artifact as untrusted input: reading a PR number from it is fine, but running a binary built from the PR inside the privileged workflow is a vulnerability.

Restricting pull_request_target to PRs with a safe to test label is only a temporary fix, because an attacker can push changes after the label is applied but before the job starts.

Test it yourself

Run all of this on your own repositories only. Use a throwaway repo for the injection test.

These greps find privileged triggers, risky expressions, unpinned actions and hardcoded-looking keys.

grep -rnE 'pull_request_target|workflow_run' .github/workflows
grep -rnE 'github\.event|github\.head_ref' .github/workflows
grep -rnE 'uses: [^ ]+@' .github/workflows | grep -vE '@[0-9a-f]{40}'
grep -rnEi '(key|token|secret|password)[a-z_]*:[[:space:]]*"?[A-Za-z0-9_.-]{8,}' .github/workflows

Bad results:

  • a pull_request_target hit next to a checkout of github.event.pull_request.head.sha
  • a github.event or github.head_ref expression inside run:
  • a hardcoded value

A good result is no hits, or hits you checked one by one.

To test script injection, put the unsafe issue-title workflow in the throwaway repo and open an issue titled $(echo INJECTED). If the run log says New issue: INJECTED, the shell executed your title. In the fixed version the log prints the title as literal text.

To test fork pull requests, add a step with env: API_KEY: ${{ secrets.API_KEY }} and run: test -n "$API_KEY" && echo present || echo empty. Then open a PR from a second account's fork and read the run log:

  • empty: the secret was withheld, which is what you want.
  • present: a privileged trigger (or the private-repo setting that sends secrets to fork PR workflows) is handing secrets to fork PRs.
TIP

Never print a secret to test a workflow. Redaction is not guaranteed, because a transformed secret, for example Base64 or URL-encoded, is not masked. If a secret reaches a log, delete the log and rotate the secret.

Fix prompt you can paste

Paste this into Cursor or Claude Code at the repo root. Read the diff afterwards: a change that quietly widens permissions is easy to miss.

FIX PROMPT
Audit every file in .github/workflows/ for security problems.
Report each finding as file:line, fix it, and explain the change in one sentence.
Look for:
1. Hardcoded keys, tokens or passwords. Replace them with ${{ secrets.NAME }}
   and list the secret names I must create. Never print secret values.
2. pull_request_target or workflow_run combined with actions/checkout of
   github.event.pull_request.head.sha or head.ref, or any step that runs
   install, build or test on that code. Switch build/test jobs to
   pull_request with permissions: contents: read. If a job must build the PR
   AND comment or label, split it into an unprivileged pull_request workflow
   that uploads an artifact and a workflow_run workflow that comments. If a
   job only comments or labels, it may keep pull_request_target but must not
   check out or run PR code.
3. ${{ github.event.* }} or ${{ github.head_ref }} inside run: or script:
   blocks. Move each into an env: variable and use a quoted shell variable.
4. Missing permissions: blocks. Add contents: read at workflow level and
   raise it per job only where needed.
5. Third-party actions referenced by tag or branch. Pin them to a full commit
   SHA with a version comment. Do not invent SHAs: list the ones I need to
   look up in each action's own repository.
6. Deploy jobs using production secrets without an environment: key. Add
   environment: production to the job and tell me to enable required
   reviewers in Settings.
7. actions/checkout steps without persist-credentials: false. Add it unless
   the job needs to push.
8. workflow_run jobs that execute code from a downloaded artifact. Flag them
   and explain the risk.
Do not change what the workflows do beyond these fixes. End with a summary
table of findings and fixes.

FAQ

Are GitHub Actions secrets available to pull requests from forks?

Not by default. With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository. The pull_request_target and workflow_run triggers run with secrets, so they need care.

Is pull_request_target safe to use?

It's safe for jobs that only label or comment and never check out or run the PR's code. Combined with an explicit checkout of an untrusted PR, it can lead to repository takeover. GitHub's docs say to avoid it when it isn't necessary.

How do I pin actions to a commit SHA?

Put the full-length commit SHA after the @ in uses: and add the version as a comment. Copy the SHA from the action's own repository, not a fork.

What should I do if a secret shows up in a workflow log?

Delete the log and rotate the secret. Redaction is done by the runner and only works if it finds an exact match, so transformed or structured values can slip through. See how to rotate API keys after a breach.

Can everyone with access to my repo read its secrets?

Not everyone, but anyone with write access to the repository can read all secrets configured in it, so only give write access to people you trust. Put production keys in an environment with required reviewers so a job can't read them until someone approves.
