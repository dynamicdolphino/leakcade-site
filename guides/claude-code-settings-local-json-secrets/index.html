Claude Code settings.local.json secrets: check your repo and fix it

Updated Nov 8, 20266 min read

Claude Code settings.local.json secrets are an easy leak to miss. When you pick "Yes, and don't ask again", Claude Code can save the exact command in .claude/settings.local.json, password and all. Security firm Apiiro found 1,122 public copies of that file on GitHub with at least one secret inside. Here is how to check your repo and its history, what to rotate, and how to keep secrets out of the file from now on.

How Claude Code settings.local.json secrets happen

Claude Code asks before it runs most shell commands. If you choose "Yes, and don't ask again", it saves an allow rule in .claude/settings.local.json in your project, so the same command runs without asking next time.

Sometimes the rule is a pattern, like npm test *. Sometimes it is the exact command you approved. If that command had a password or token typed into it, for example PGPASSWORD=... psql or sshpass -p ..., the secret is now in a plain JSON file in your project folder.

Claude Code tries to keep the file out of git. The first time it writes the file in a repo, it adds it to your global git excludes on that computer. That protects you on that one machine. It doesn't help if the file was already committed, if you created it by hand, or if a teammate clones the repo on a machine without that exclude, because the project's own .gitignore never mentions it.

WATCH OUT

Deleting the file in a new commit doesn't undo a leak. Old versions stay in git history and in forks.

What Apiiro found on public GitHub

Apiiro searched public GitHub and found 104,185 copies of the file in 103,617 repositories. About 1.1% of them, 1,122 copies, held at least one secret, 1,379 different secrets in total. They didn't test whether the secrets still worked, but one company they notified confirmed its key had been live.

Two more numbers matter for you. Older versions of the file held 734 more secrets in 509 repos that no current copy has, usually because the file was deleted. And common scanners missed many of these files: of the 1,122, gitleaks flagged 564 and TruffleHog 643, and neither flagged 215. Most misses were passwords typed inside commands, which look like ordinary words to a scanner that hunts for known key formats.

So "my secret scanner was green" is not enough here. Open the file and read it.

Check your repo in two minutes

Run these in the root of each repo you use with Claude Code.

# 1. Is the file tracked right now?
git ls-files .claude/

# 2. Was it ever committed? (also finds deleted versions)
git log --all --oneline -- .claude/settings.local.json .claude/settings.json

# 3. Show what old versions contained
git log --all -p -- .claude/settings.local.json | grep -Ei 'password|passwd|token|secret|key|sshpass|PGPASSWORD|mysql -p|://[^ ]*:[^ ]*@'

# 4. Why is it ignored on this machine? (global exclude vs .gitignore)
git check-ignore -v .claude/settings.local.json

If step 4 points to a global excludes file and not to your repo's .gitignore, the protection lives only on your computer.

On GitHub, search your account or organization for the file across all repos. Code search only covers the current default branch, so step 2 is still needed per repo:

path:.claude/settings.local.json org:YOUR-ORG

Also open the file on your own laptop, even if it was never committed. It is plain JSON, and it can end up in a zip, a Docker image, an npm package or a synced folder.

Fix it: rotate first, then clean up

Do these in order. Rotation comes first, because cleaning git doesn't make a leaked secret safe again.

  1. Rotate every secret the file ever held

    Change each database password, token, SSH login and API key found in the current file and in old versions. Start with anything paired with a public server address, because those give direct access. See rotate keys after a breach.

  2. Stop tracking the file

    Run git rm --cached .claude/settings.local.json, then add .claude/settings.local.json to the repo's own .gitignore and commit both. Your local copy stays.

  3. Clean the local file

    Open .claude/settings.local.json and delete every allow rule with a password, token or key in it. Delete rules you don't remember approving, too.

  4. Check the shared settings.json

    Teams commit .claude/settings.json on purpose. Apiiro found secrets in 298 copies of it, mostly in allow rules. Make sure it only holds patterns and variable names.

  5. Decide on history

    If the repo is public or has forks, assume the old secret is known, even after a rewrite. Rewriting history is optional once you have rotated. See find secrets in git history.

Do the same in every repo where you used Claude Code, not just the one that made the news for you.

Stop it happening again

Keep secrets out of the commands you approve. Put them in env vars or a secrets manager and refer to them by name, so the saved rule holds $DATABASE_URL and not the password.

Approve patterns instead of one-off commands. A rule like Bash(npm run test:*) is safe to save. A rule with a full connection string in it is not.

Add these lines to every project's .gitignore, so the protection travels with the repo:

.claude/settings.local.json
.env
.env.*

The same goes for other agent folders. Treat .cursor/, .gemini/ and agent chat logs like .env files: they can hold secrets on your laptop and in your repo. For the wider setup, see the Cursor and Claude Code security checklist.

TIP

Before you click "don't ask again", read the command once. If you can see a password in it, click Yes only for this time.

FAQ

Is .claude/settings.local.json ignored by git automatically?

Only on your computer. Claude Code adds it to your global git excludes the first time it writes the file, but not to the project's .gitignore. If it was already committed, or a teammate clones the repo, it can still be tracked. Add it to .gitignore yourself.

I deleted the file. Am I safe?

No. Old versions stay in git history and in forks. Rotate every secret the file ever held, then stop tracking it.

Will gitleaks or TruffleHog catch it?

Not reliably. In Apiiro's test, neither tool flagged 215 of the 1,122 files with secrets, mostly passwords typed inside commands. Open the file and read it.
