Supabase storage policies: keep users out of each other's files

Updated Oct 22, 20264 min read

Supabase storage policies are RLS policies on the storage.objects table. A policy that only checks bucket_id = 'documents' doesn't say whose file it is, so anyone it applies to can list and download every file in the bucket. A public bucket skips the download check completely.

QUICK CHECKLIST

  • Private files live in private buckets
  • Every select policy on a private bucket checks the owner or folder, not just bucket_id

  • File size limit and MIME types set on the bucket

How access works in Supabase Storage

Every file is a row in storage.objects with a bucket_id, a path in name and an owner_id. Supabase's docs say Storage allows no uploads without RLS policies, and you open each operation with a policy: insert for uploads, select for downloads and listing, update and delete for changes. Upserts need select and update as well.

Public and private buckets differ only in downloads. In a public bucket, anyone with a file's URL can download it, with no policy involved. Uploads, deletes and moves still go through your policies in both, the same way RLS works on your tables.

NOTE

Public buckets are fine for avatars and product images. Supabase's docs list user profile pictures and blog content as examples. Contracts, invoices and ID scans belong in a private bucket.

Four patterns to look for

Select by bucket only. for select using (bucket_id = 'documents') without a to role applies to signed-out visitors. A plain select policy also lets people list the bucket's contents, and that includes public buckets.

Logged in means allowed. bucket_id = 'uploads' and auth.role() = 'authenticated' lets every account read, or with update and delete, change every file. One repo named such a policy "Applicants can view own presentation materials" and checked auth.role() = 'authenticated' or auth.role() = 'anon', which is everyone.

Private files in a public bucket. insert into storage.buckets (id, name, public) values ('resumes', 'resumes', true). Anyone who has a file's URL can download it, and a broad select policy lets them list the names.

Uploads without a login. for insert with check (bucket_id = 'avatars') with no role lets strangers fill your bucket. Supabase's Next.js tutorial uses this policy for avatars as a demo, and two of the repos we flagged had copied it.

What we found in public repos

We searched public GitHub code for migrations with both storage.buckets and select policies on storage.objects and read the SQL from 30 repos. Our check flagged 13. The most serious were a public evidence bucket in a safety-report app with a policy that lets anyone list it, a public resumes bucket next to a read policy for every bucket, and the "own presentation materials" policy above. Most other flags were uploads open to signed-out visitors. Three were read policies on picture buckets with other names (portfolio, records, stores) that were probably meant to be public.

We picked these files because they matched the search, so this is not a rate across all Supabase apps. We read every flagged policy by hand and didn't contact the repo owners.

How to write safe Supabase storage policies

  1. Make private buckets private

    update storage.buckets set public = false
where id = 'documents';

  2. Put each user's files in their own folder

    Upload to {user_id}/file.pdf and check the first folder:

    create policy "own folder: read" on storage.objects
for select to authenticated
using (
  bucket_id = 'documents'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);
    Use the same check in with check for insert, in using for delete, and in both for update.

  3. Or check owner_id

    For files the user uploaded themselves, Supabase's ownership docs use owner_id = (select auth.uid()::text). Files uploaded with the service key have no owner.

  4. Serve private files with signed URLs

    createSignedUrl(path, 60) gives a link that expires. getPublicUrl only works for public buckets and never expires.

  5. Limit uploads

    Set a file size limit and allowed MIME types on the bucket, and keep uploads behind a login. Login-only deletes have the same problem as on tables, see Supabase delete policies.

FAQ

Are Supabase storage buckets public by default?

No. Buckets are private by default. A public bucket lets anyone with a file's URL download it. Uploads and deletes still need policies.

How do I let users only access their own files in Supabase Storage?

Upload to a folder named after the user id and add policies with (storage.foldername(name))[1] = (select auth.uid()::text) for select, insert, update and delete.

Why can anyone list files in my public bucket?

A select policy on storage.objects allows listing. Public buckets don't need a select policy for downloads, so remove it or restrict it.

What's the difference between getPublicUrl and createSignedUrl?

getPublicUrl builds a permanent link that only works for public buckets. createSignedUrl creates a link to a private file that expires after the time you set.
