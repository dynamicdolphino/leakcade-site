NoSQL injection in Express and MongoDB: the login bypass and how to fix it

Updated Oct 22, 20268 min read

NoSQL injection happens when your Express route passes req.body straight into findOne() or find(). An attacker sends {"$ne": null} where you expected a string, and MongoDB treats it as a query operator ($ne means "not equal"). On a login route, that logs them in without a password. Check that every input is a string, then add express-mongo-sanitize and Mongoose's sanitizeFilter as safety nets.

What NoSQL injection is and why Mongoose apps get it

NoSQL injection is when an attacker interferes with the queries your app sends to a NoSQL database. PortSwigger lists what that can lead to: bypassing authentication, extracting or editing data, denial of service, and in some setups running code on the server.

MongoDB's own FAQ says traditional SQL injection isn't a problem because a client builds a BSON object (MongoDB's binary JSON format) instead of gluing a string together. The catch is that Express turns the JSON body into a JavaScript object for you, so an attacker who sends an object where you expected a password makes req.body.password an object.

AI tools write User.findOne({ email, password }) constantly because it's short and it works in the demo. Nothing in that line checks that password is a string. If you're wondering how much to trust generated code in general, read is AI-generated code secure.

NOTE

PortSwigger calls this operator injection: the attacker uses MongoDB query operators like $ne to change what a query means. The other kind, syntax injection, breaks out of a string. It mostly shows up when you build query strings or $where JavaScript by hand.

How a NoSQL injection login bypass works

A normal login request looks like this:

{"email":"ana@example.com","password":"hunter2"}

The attacker sends this instead:

{"email":{"$ne":null},"password":{"$ne":null}}

$ne means "not equal", so your filter now reads "any user whose email isn't null and whose password isn't null". MongoDB returns the first match, so PortSwigger notes you're logged in as the first user in the collection, which could be an admin depending on your data.

To target one account, the attacker uses a guessed email and {"$ne": ""} for the password. PortSwigger's example uses $in with a list of likely names such as admin and superadmin.

The same trick works from a URL. username[$ne]=invalid can turn into an object during query parsing, depending on your Express settings. So search and filter routes that read req.query are exposed too.

Two more operators do damage beyond login:

  • $where runs a JavaScript expression inside MongoDB. MongoDB's FAQ lists $where, mapReduce, $accumulator and $function as operations that run arbitrary JavaScript, and tells you to take care. PortSwigger shows attackers pulling a password out one character at a time this way.
  • $regex lets an attacker probe values by pattern, again one character at a time. A regex you let users supply can also be slow to run, so it's a way to burn your database's CPU.

It's the same weakness as in SQL: untrusted input changes the meaning of the query. If you use an ORM, the SQL injection ORM guide covers the relational version.

OperatorWhat it does to youFix
$ne, $in, $gtMatches any user and skips the password checkValidate as string
$whereRuns JavaScript inside MongoDBNever use user input

WATCH OUT

If your users collection stores plain text passwords, hash them with bcrypt or argon2 (one-way functions that store a scrambled version instead of the password) and force a reset. See password reset security for doing the reset safely.

express-mongo-sanitize and Mongoose sanitizeFilter

Validation is the fix. These two libraries are a backup, so one forgotten route doesn't become a hole. OWASP says positive server-side validation is not a complete defense on its own, which is a good reason to layer them.

express-mongo-sanitize is Express middleware (code that runs on every request before your routes). Per its README, it searches req.body, req.query, req.params and req.headers for keys that start with $ or contain a . and removes them, or swaps the characters if you set replaceWith. Add it after the body parser and before your routes.

import express from "express"
import mongoose from "mongoose"
import mongoSanitize from "express-mongo-sanitize"

mongoose.set("sanitizeFilter", true)

const app = express()
app.use(express.json())
app.use(mongoSanitize()) // Express 4 only, see the warning below

The sanitizeFilter option is Mongoose's own layer. With it on, Mongoose wraps nested objects whose keys start with $ in $eq. So {"$ne": null} is searched as a literal value and matches nothing. If you write operators yourself, like { age: { $gt: 18 } }, mark them with mongoose.trusted().

It only applies to query filters. It does not touch aggregate() pipelines, and it won't stop a top-level $where key if you pass the whole req.body as the filter. Validation still has to cover those routes.

WATCH OUT

The express-mongo-sanitize README describes it as Express 4.x middleware. On Express 5 it crashes on requests with a query string, because Express 5 doesn't let middleware reassign req.query. On Express 5, skip app.use(mongoSanitize()). Call mongoSanitize.sanitize(req.body) and mongoSanitize.sanitize(req.params) yourself, and rely on validation plus sanitizeFilter for query strings. Keep the type checks either way.

How to fix NoSQL injection, step by step

Do these in order. The first two close the login bypass on their own.

  1. Validate every input as a string

    Parse req.body with a schema where each field is z.string() with a max length. Return 400 when parsing fails. An object where a string belongs never reaches MongoDB.

  2. Keep the password out of the filter

    Find the user by email only, then compare with bcrypt.compare against the stored hash. A login that puts password in findOne() is wrong even without injection.

  3. Add express-mongo-sanitize

    On Express 4, call app.use(mongoSanitize()) after express.json() and before your routes. It strips $ and . keys from the request. On Express 5, use the manual sanitize calls from the warning above.

  4. Turn on Mongoose sanitizeFilter

    Call mongoose.set("sanitizeFilter", true) once at startup. Wrap operators you write yourself with mongoose.trusted().

  5. Tame $where and $regex

    Never put user input into $where. If you run your own mongod, MongoDB's FAQ says you can disable server-side JavaScript with security.javascriptEnabled: false or --noscripting. For search, escape the text before it becomes a pattern. Wrap the operator in mongoose.trusted() too, because step 4 turned on sanitizeFilter and would otherwise treat your own $regex as a literal value:

    const escapeRegex = (s: string) => s.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")

const q = z.string().max(50).parse(req.query.q) // throws on objects
const items = await Product.find({
  title: mongoose.trusted({ $regex: escapeRegex(q), $options: "i" }), // trusted: needed with sanitizeFilter on
})

    Catch the parse error and return 400.

  6. Slow down guessing

    Add login rate limiting. It caps how fast anyone can probe your login route.

Test it yourself

WATCH OUT

Run these only against your own app, on your machine or a staging copy. Don't point them at anyone else's site.

  1. Start the app locally with one test user, for example ana@example.com.
  2. Send the operator payload:
curl -i -X POST http://localhost:3000/login \
  -H "Content-Type: application/json" \
  -d '{"email":{"$ne":null},"password":{"$ne":null}}'

Bad result: a 200 with a user id or a session cookie. Good result: 400 from validation, or 401.

  1. Try one operator at a time. Send your real test email with {"$ne":""} as the password. A 200 means the filter still takes operators.
  2. Check routes that read req.query: curl -g 'http://localhost:3000/items?q[$ne]=x'. This only exercises operator parsing if your app uses the extended (qs) query parser, which is the Express 4 default. Bad: results that would not match a literal search come back. Good: 400.
  3. If a route passes the whole body as the filter, add "$where":"0" to one request and "$where":"1" to another. PortSwigger says a difference between the responses suggests your JavaScript expression is being evaluated.
  4. Search your code for risky calls:
grep -rnE "(find|findOne|updateOne|deleteOne|countDocuments)\([[:space:]]*req\.(body|query|params)" src
grep -rn "\$where" src

These only catch the direct form. Also review every handler that destructures from req.body or req.query and passes those values into a filter. The grep won't find findOne({ email, password }).

To see what the sanitizer would strip without changing anything, set dryRun: true and an onSanitize callback in mongoSanitize(). Both options are in the README. Every log line is a route that was passing operators through.

TIP

Add the step 2 curl as an automated test. A request with $ne in both fields should return 400 or 401, and it keeps the bug from coming back when someone edits the route later.

FAQ

Does Mongoose protect against NoSQL injection by default?

No. A schema doesn't stop an operator object like {"$ne": null} from reaching your filter. Validate every input as a string, and turn on the sanitizeFilter option as a second layer.

What does express-mongo-sanitize do?

It's Express middleware that searches req.body, req.query, req.params and req.headers for keys that start with $ or contain a .. By default it removes them. You can set replaceWith to swap the characters instead. Its README describes it as Express 4.x middleware.

Isn't MongoDB safe from injection because queries are BSON objects?

Only from the string-concatenation kind. MongoDB's FAQ says traditional SQL injection isn't a problem because clients build BSON objects. If you pass an attacker-controlled object into a filter, they can still add operators. $where and similar operations also run JavaScript, so never build them from user input, and disable server-side JavaScript on your own mongod if you don't need it.

What is mongoose sanitizeFilter?

It's a Mongoose option that wraps nested objects with $ keys in $eq, so an injected operator is treated as a literal value. Operators you write yourself, like { $gt: 18 }, need mongoose.trusted(), or Mongoose treats them as literal values too.

Do I still need validation if I use a sanitizer?

Yes. A sanitizer only removes keys that start with $ or contain a dot, so an array or a number in a string field still gets through. Validation makes sure each field is the type you expect, and OWASP recommends positive server-side validation as part of preventing injection.
