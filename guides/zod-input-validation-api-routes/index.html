Input validation in API routes: zod schemas for Next.js

Updated Oct 24, 20266 min read

Input validation in API routes means checking every body, query string and URL param on the server before your code uses it. In Next.js, run each request through a zod schema, reject unknown keys, cap lengths, and write only the fields the schema returns. Never pass req.json() straight to your database, because the client decides what is in it.

QUICK CHECKLIST

  • Parse every body, query and param with a zod schema
  • Use z.strictObject so unknown keys return a 400
  • Cap string lengths, array sizes and body bytes
  • Write result.data, never req.json() or a spread
  • Take user id and role from the session, not the body
  • Test with an extra role field and an oversized body

Why input validation in API routes matters

A route handler is a public URL. Your form sends tidy JSON, but anyone can send the same request with curl (a command-line HTTP client) and put whatever they like in it.

Input validation checks that data fits your rules before the app uses it. OWASP's cheat sheet asks for allowed sets for fixed choices, a type plus a range for numbers, length limits for strings and item counts for arrays. A zod schema (zod is a TypeScript validation library) writes those rules once.

Validation is one layer. A valid user id doesn't mean the caller may touch that user, so you still need ownership checks and parameterized queries (see SQL injection through an ORM).

How mass assignment and oversized input get through

Mass assignment means a request carries fields you never meant to accept, and your code saves them. OWASP notes that attackers can guess field names without seeing your source. Typical targets are role, isAdmin, plan, credits, ownerId and emailVerified.

Spreading the body is the shortest code that works, so AI tools reach for it. With Prisma (a Node.js database library) it looks like prisma.user.update({ data: { ...body } }), and with Supabase like supabase.from('profiles').update(body). Prisma rejects keys that aren't columns, but it accepts every real column.

Oversized or odd input causes other trouble:

  • A 5 MB bio string fills your database and slows every page that shows it.
  • A huge array makes your own loop burn CPU.
  • A price or userId trusted from the body (see Stripe price tampering).
  • An object where you expected a string can change what a query means (NoSQL injection).
WATCH OUT

Browser maxlength attributes give fast feedback, but OWASP lists client-only checks as a common pitfall. Validate on the server.

Before and after: stop spreading req.json()

Here is how to validate a request body with zod in a Next.js route handler. The wrong version spreads the body. The fixed version names every field and writes only what the schema returns.

What changed:

  • z.strictObject accepts three named fields and returns an error for anything else, such as role.
  • Each field has a type and a cap. theme is an enum, so it must match one value from a fixed list.
  • The write uses result.data, never body. The user id comes from the session, and select limits the response to four columns.
NOTE

Plain z.object strips unknown keys, so they never reach result.data. A strict schema rejects the request instead, so probing shows up in your 400 logs.

How to validate API route input with zod, step by step

Write the helper once. After that, every route is a schema plus three lines.

TIP

These snippets use the Zod 4 API. On Zod 3, write z.object(...).strict() instead of z.strictObject(...), .passthrough() instead of z.looseObject(), and z.string().email() or z.string().uuid() instead of z.email() or z.uuid().

  1. Write one schema per route

    Name every field. Give strings a .max(), numbers .int().min().max(), choices z.enum([...]), and arrays a .max() on count and on each item. Use z.strictObject for anything that writes data. Never accept userId, role, plan, ownerId or price from the body. Read them from the session or compute them on the server.

  2. Add one shared check helper

    Use safeParse, because parse throws and turns a bad request into a 500. Return issue paths and messages, not the raw input.

    // lib/validate.ts
import { z } from "zod";

type Result<T> = { ok: true; data: T } | { ok: false; response: Response };

export function check<S extends z.ZodType>(schema: S, input: unknown): Result<z.output<S>> {
  const parsed = schema.safeParse(input);
  if (parsed.success) return { ok: true, data: parsed.data };
  const errors = parsed.error.issues.map((i) => ({
    path: i.path.map(String).join("."),
    message: i.message,
  }));
  return {
    ok: false,
    response: Response.json({ error: "Invalid input", errors }, { status: 400 }),
  };
}

  3. Cap the body size before you parse

    OWASP says to apply size limits before parsing. Check Content-Length first, then count bytes while reading, since that header can be missing or wrong.

    // lib/validate.ts (same file)
const MAX_BYTES = 100_000;

async function readLimited(req: Request): Promise<string | null> {
  if (Number(req.headers.get("content-length") ?? 0) > MAX_BYTES) return null;
  const reader = req.body?.getReader();
  if (!reader) return "";
  const decoder = new TextDecoder();
  let size = 0;
  let text = "";
  for (;;) {
    const { done, value } = await reader.read();
    if (done) return text + decoder.decode();
    size += value.byteLength;
    if (size > MAX_BYTES) {
      await reader.cancel();
      return null;
    }
    text += decoder.decode(value, { stream: true });
  }
}

export async function parseBody<S extends z.ZodType>(req: Request, schema: S) {
  const text = await readLimited(req);
  if (text === null) {
    return { ok: false as const, response: new Response("Body too large", { status: 413 }) };
  }
  let json: unknown;
  try {
    json = JSON.parse(text);
  } catch {
    return { ok: false as const, response: new Response("Invalid JSON", { status: 400 }) };
  }
  return check(schema, json);
}

    Pick MAX_BYTES to fit your largest real request. Your host and Next.js may set their own limits, so check their current docs and keep your own cap.

  4. Validate query strings and params too

    Query values arrive as strings, so numbers need z.coerce.number(). Pass Object.fromEntries(req.nextUrl.searchParams) to check(). For dynamic segments, validate await params the same way, for example with z.object({ id: z.uuid() }).

  5. Repeat it inside every server action

    A server action is a function marked use server that a form calls. Next.js docs say anyone can reach an exported one with a direct POST request, so server action validation and auth checks belong inside each action. Check the session first, then run safeParse on the form values. More in Next.js server actions security.

Coercion, length and size traps

z.coerce calls the JavaScript constructor on whatever arrives: Boolean(input), String(input) or Number(input). The table shows where that goes wrong.

What it doesSafer move
z.coerce.number()Empty string becomes 0Add .min(1), or preprocess "" to undefined
z.coerce.boolean()The string "false" becomes trueUse z.enum(["true","false"])
z.coerce.string()null becomes the string "null"Use plain z.string()

Coercion calls JavaScript constructors, so odd input can still pass.

Coerce only where the input really is a string, like query params and form data. In JSON bodies, send real numbers and booleans and validate them as such.

Two more traps:

  • Zod counts string length in characters, not bytes, so a .max(500) field can hold more than 500 bytes. Keep the body cap too.
  • z.looseObject() (.passthrough() in older code) keeps unknown keys. Don't use it for anything you write.

Test it yourself

WATCH OUT

Run these only against your own app, on localhost or your own staging. Don't point them at anyone else's site.

Copy the Cookie header from your browser's Network tab after you log in, then send requests the form would never send.

URL=http://localhost:3000/api/profile
COOKIE="YOUR_SESSION_COOKIE"
send() { curl -i -X PATCH "$URL" -H "Content-Type: application/json" -H "Cookie: $COOKIE" "$@"; }

# 1. Extra key. Expect 400.
send -d '{"name":"Test","role":"admin"}'

# 2. Wrong type. Expect 400.
send -d '{"name":["a","b"]}'

# 3. Huge body. Expect 413.
node -e "console.log(JSON.stringify({bio:'a'.repeat(300000)}))" > huge.json
send --data @huge.json

Bad results: a 200 on test 1, a 500 with a stack trace on test 2, or a changed role in your database. Good results: a 400 listing the offending paths on tests 1 and 2, a 413 on test 3, and an unchanged row.

In the browser, delete the maxlength attribute in devtools and submit 10,000 characters. You should get a validation error back.

FAQ

How do I validate a request body with zod in a Next.js route handler?

Read the body with await req.json() in a try/catch (return 400 on invalid JSON), then run schema.safeParse(body). Return a 400 if parsed.success is false, otherwise use parsed.data. The parseBody helper in this guide does this and caps body size.

What is mass assignment with Prisma or Supabase?

It happens when you pass request data straight into data or .update(). Prisma rejects keys that aren't columns but accepts every real column, so a client can set role or plan if they exist. Pick fields with a strict schema instead.

Does z.object reject extra keys?

No. By default z.object strips unknown keys from the output. Use z.strictObject, the Zod 4 form of .strict(), to return an error instead.

Do server actions need validation too?

Yes. The Next.js docs say an exported server action can be reached with a direct POST request. Validate input and check auth inside each action.
