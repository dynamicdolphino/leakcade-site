Supabase getSession vs getUser: stop trusting the cookie on your server

Updated Oct 24, 20267 min read

Supabase getSession vs getUser comes down to one rule: on the server, don't trust getSession(), because it reads the session from a cookie without checking it. Use getClaims() to protect pages and data. Reach for getUser() when you need a fresh record from the Auth server or must catch revoked sessions, and keep getSession() for code that needs the raw tokens.

QUICK CHECKLIST

  • Never read session.user to authorize anything
  • Call getUser() before sensitive actions
  • Keep authenticated routes dynamic: no ISR, no CDN cache

Supabase getSession vs getUser vs getClaims: the short version

Supabase Auth has three ways to ask who the current user is.

  • getSession() loads the session from storage. On the server that's the cookie, and nothing is re-validated.
  • getClaims() verifies the signature of the access token (a JWT, the signed token that proves who is logged in) and returns its claims, such as the user id (sub) and expiry (exp).
  • getUser() calls your project's Auth server and returns the current user record.

Supabase's docs warn against using the user object from getSession() for authorization decisions.

NOTE

getClaims() is meant for JWTs issued by Supabase Auth. If you mint your own JWTs with an imported key, verification may fail, so use a JWT verification library for those.

How a forged cookie gets past getSession(), and the fix

On the server, the session comes from the cookie the browser sends. The browser belongs to whoever uses your site, including an attacker. Anyone can forge the session cookie, and Supabase's docs say that trusting it without verification lets an attacker render another user's page.

The attack path is short:

  1. The attacker edits the user id inside their own cookie.
  2. Your server reads it with getSession() and believes it.
  3. Your code uses that id for an admin check, a page or a query.

Queries through the user's own client still carry a token that Supabase checks before applying row level security (RLS), the database rules that limit which rows each user can read. The danger is anything your own code decides from session.user. The worst case is a user id handed to a service-role client, an admin client that bypasses RLS.

WATCH OUT

A service-role client skips RLS. If you pass it an id read from getSession(), the cookie decides whose data comes back.

Ask getClaims() instead and use claims.sub. Supabase RLS mistakes covers the policy side.

How getClaims verifies the token, and what it can't catch

A Supabase access token is a JWT with a header, a payload and a signature. The signature proves the payload wasn't edited, and exp marks when the token should stop being trusted.

New projects sign tokens with asymmetric keys: a private key signs and a public key checks. With these, Supabase getClaims verifies locally against a cached copy of your project's public keys, so most calls skip the Auth server.

Supabase publishes the public keys as a JWKS (JSON Web Key Set, a public list of keys used to check signatures) at https://YOUR_PROJECT_REF.supabase.co/auth/v1/.well-known/jwks.json. If you can't use the client library, verify a Supabase JWT against that URL with a library like jose. Pin the issuer (https://YOUR_PROJECT_REF.supabase.co/auth/v1) and the audience (authenticated).

If your project still uses an HS256 shared secret (one secret string that both signs and checks tokens), getClaims() calls the Auth server to validate. Supabase strongly recommends against verifying with that secret yourself. Whoever holds it can impersonate your users, and it leaks easily through a NEXT_PUBLIC_ variable (see public env vars).

With asymmetric keys, getClaims() checks only signature and expiry. The token of a revoked session stays valid until it expires. Supabase says the only way to detect an ended session on the server is getUser().

Caching and ISR can hand one user's session to another

When @supabase/ssr refreshes a session on the server, the new token goes out in a Set-Cookie header. If ISR (incremental static regeneration, where Next.js saves a rendered page and reuses it) or a CDN (a network that serves saved copies of pages) caches that response for someone else, their browser stores your token and they are signed in as you.

  • Don't use ISR on routes that handle auth or can trigger a refresh. Add export const dynamic = 'force-dynamic' to pages that need a signed-in user.
  • From @supabase/ssr v0.10.0, the library passes Cache-Control, Expires and Pragma to your setAll callback on refresh. Apply them to the response. On older versions, set Cache-Control: private, no-store yourself.
  • Create the Supabase client inside the request handler. On Vercel's Fluid compute, a module-level client can be reused across requests from different users.
TIP

Next.js 16 renamed middleware.ts to proxy.ts. On version 15 and earlier a proxy.ts file is never called, so sessions don't refresh. Don't make the proxy your only gate. Check inside each route and server action too, as in Next.js middleware authentication.

How to switch from getSession to getClaims, step by step

  1. Find every server use of getSession

    Search your repo for getSession(. Note which hits run on the server and which run in client components.

  2. Swap identity checks to getClaims

    Read data?.claims.sub. On an error or a missing id, return 401 from route handlers and server actions, and redirect to login from Server Components and the proxy. Every server action is a public endpoint, so do this there too.

  3. Keep getSession for tokens only

    If you forward the access token to another service, getSession() is fine for that.

  4. Add getUser where revocation matters

    Use it before account deletion, email changes, payments and admin actions:

    const { data: { user }, error } = await supabase.auth.getUser()
if (error || !user) return new Response('Unauthorized', { status: 401 })

  5. Keep sessions out of caches

    Add force-dynamic to authenticated pages, send private, no-store where needed, and build the client inside each request.

  6. Check your signing keys

    In the Supabase dashboard, see whether your project uses asymmetric keys or an HS256 shared secret. If it's the shared secret, keep it out of frontend code.

Test it yourself

Run these on your own app only, ideally against a dev or staging project.

  1. Search for risky calls:
grep -rn "getSession(" --include="*.ts" --include="*.tsx" --exclude-dir=node_modules --exclude-dir=.next .

Bad: hits in route handlers, server actions, Server Components or the proxy that feed an access decision. Good: hits only in client components or code that forwards the token.

  1. Edit the cookie. Sign in, then open DevTools, Application, Cookies. Find the cookie named like sb-YOUR_PROJECT_REF-auth-token. Change the user id or email inside the session JSON and reload a server-rendered page.
  2. Bad: the page shows the edited identity.
  3. Good: it shows your real account or signs you out.
  1. Check the revoked session gap. Sign in as the same user in two browsers, then call signOut() in browser A. In browser B, hit one route that uses getClaims() and one that uses getUser(). On asymmetric-key projects the getClaims() route may keep answering until the access token expires. The getUser() route should return 401.
  1. Check caching. In DevTools, Network, click the document request of an authenticated page. Bad: a public or s-maxage Cache-Control on a response that sets a cookie. Good: private, no-store on every response that sets a cookie.

FAQ

Is supabase.auth.getSession() safe to use on the server?

No, not for deciding who the user is. It reads the session from the cookie without revalidating it, and anyone can forge the session cookie. Use getClaims() or getUser() for identity, and keep getSession() for cases where you need the raw tokens.

What is the difference between getClaims and getUser in Supabase?

getClaims() verifies the token's signature and returns the claims inside it. On asymmetric keys it checks locally against cached public keys, so most calls skip the Auth server. getUser() always calls the Auth server and returns the latest user record, so it also notices a revoked session.

Does getClaims notice that a user signed out on another device?

Not on projects with asymmetric signing keys. getClaims() checks signature and expiry, and an unexpired token stays valid after the session behind it was revoked. Call getUser() where that gap matters.

How do I verify a Supabase JWT on my own server?

If you use asymmetric signing keys, verify against your project's JWKS at /auth/v1/.well-known/jwks.json with a library like jose. If you use an HS256 shared secret, Supabase recommends sending the token to the Auth server at /auth/v1/user instead of checking it yourself.

Can ISR break Supabase auth?

Yes. If a cached response includes a Set-Cookie header with a refreshed token, the next visitor can be signed in as the wrong person. Don't use ISR on authenticated routes and add force-dynamic to pages that need a signed-in user.
