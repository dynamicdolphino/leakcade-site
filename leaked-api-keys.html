Leaked API keys in vibe-coded apps

Updated Oct 22, 20263 min read

If your repo is public and a key was ever committed, treat it as a leaked API key, even if you deleted it later. Bots scan public GitHub repos for secrets all the time. GitHub counted more than 39 million leaked secrets across the platform in 2024. Here's how keys leak in AI-built apps and what to do, in order.

How a leaked API key ends up public

  • The AI puts the key directly in config.js "for now".
  • .env isn't in .gitignore, so the first git add . commits it.
  • A key is deleted in the latest commit but still sits in git history, where anyone can read it.
  • Frontend code ships a secret key to every browser, often through a VITE_ or NEXT_PUBLIC_ variable.

Hardcoded keys are one of the AI-generated code security risks we see most.

WATCH OUT

Deleting the line in a new commit leaves the old commit untouched. Anyone can still open it on GitHub or in a clone.

What to do when an API key leaked

  1. Rotate the key

    Create a new key in the provider's dashboard and revoke the old one. Do this first. The old key stays usable until you revoke it.

  2. Check what it was used for

    Look at the provider's usage, logs and billing for calls you didn't make. For cloud and payment keys, check for new resources or payouts.

  3. Move it to an environment variable

    Read the key with process.env (or your framework's server-only env) and keep the value out of the code.

  4. Ignore .env

    Add .env to .gitignore and commit a .env.example with placeholder values.

  5. Scan the whole history

    Run gitleaks git (older versions: gitleaks detect) on the repo to find every secret in every commit, not just the latest.

  6. Rewrite history only if you need to

    GitHub's docs explain how to remove secrets from git history with git filter-repo. It's optional once the key is rotated, and it doesn't remove copies people already cloned.

FAQ

Is deleting the key from my code enough?

No. The old commit still contains it, and bots may have copied it already. Rotate the key in the provider's dashboard, then clean up the code.

Do I have to rewrite my git history?

Not if the key is rotated. A revoked key in history is useless. Rewriting history with git filter-repo is worth it for secrets you can't rotate, like personal data, and it won't remove existing clones or forks.

Does GitHub detect leaked keys?

Partly. GitHub secret scanning tells many providers (like AWS and OpenAI) when their keys show up in public code, and push protection is on by default for public repos. It doesn't know every key format, so scan yourself too.

Is it safe to commit .env.example?

Yes, as long as it only has placeholder values. It shows other developers which variables they need without giving away yours.
